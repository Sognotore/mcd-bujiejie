# 麦麦不纠结

先理解用户的预算（元；空白或明确跳过则无上限），默认搭配一份主食、一份小食、一杯饮品，默认快乐餐。用户可主动选择减脂餐（400–600 大卡、蛋白质至少 25g）或健身餐（550–800 大卡、蛋白质至少 35g）；这是产品筛选规则，不是个人饮食处方。不要连续追问口味、热量或人数。没有门店时，只询问城市和附近地标，使用到店取餐。不要把示例城市当成用户所在地。

## 真实搭配流程

1. 连接用户已经配置的麦当劳 MCP（`https://mcp.mcd.cn`，Streamable HTTP），读取真实工具 schema。不要请求用户把 Token 发在聊天里，也不要读取其他项目的凭证。
2. 用 `query-nearby-stores` 查门店并让用户选择；用 `query-meals`、必要的 `query-meal-detail` 确认当前餐品、类别、规格、完整套餐及默认特调。精确字段和计价单位见 [接入要点](references/mcp-flow.md)。
3. 根据官方类别与套餐轮次确认主食/小食/饮品角色。不要只凭餐品名称猜测结构；排除随单购会员卡才可享有的价格，不自动加购会员卡。可以只读查询 `query-store-coupons`，仅对确实适用的商品试算优惠。
4. 依照 [输入契约](references/input-contract.md) 将真实结果转为归一化菜单。在本 Skill 目录执行 `node scripts/choose.mjs`，以标准输入提供 `action=candidates`，传入 mealStyle=joy/lean/fit，获取一个尚未计价确认的随机候选。预算只是上限，不刻意凑满。默认使用官方选中的特调，保留规格和数量。
5. 调用 `calculate-price` 核验完整组合。菜单价以元计，`data.price` 是以分计的最终应付，不能使用 `productPrice` 冒充最终金额。确认返回商品与所选商品一致；缺少或不正确的返回不能输出为真实推荐。
6. 把官方应付金额转换成 `quote`，以 `action=verify` 调用脚本。只有脚本确认预算及报价有效，才输出最终搭配。超过预算时重新随机候选；一次最多试算 12 份，达到上限说明“暂未找到预算内搭配，可重试或调整预算”，不宣称不存在。保留本次已拒绝的候选 key，避免重复试算。
7. 每次只输出一份：主食、小食、饮品、试算应付、门店、到店取餐及试算时间、餐型与有来源的营养参考。可替换单品可按用户要求保留；固定套餐不承诺单独锁定。新预算、餐型、门店或模式使旧结果和锁定失效。

## 重抽与失败

- 用户说“换一份”时，将上一份 key 传为 `previousKey`。用户锁定饮料时，使用已输出的精确 id，不替换成同名不同规格；全部锁定时提示先解锁。
- 锁定餐品不可售或没有其他组合时，明确说明原因，不静默替换。
- 没有授权连接、超时、401、429 或返回结构变化时，说明无法获取实时结果。不得用模型记忆补齐真实价格，不隐式切换为演示。
- 仅在用户主动要求演示时，以 `action=demo` 和 `catalog.source=demo` 运行脚本，输出必须明确写“演示搭配，非实际售价”。
- 本 Skill 只读查询和试算，不调用创建订单、领券、兑换或扣积分工具。不记录用户的原始定位、账户凭证、完整优惠券标识等信息。

## 营养数据与餐型不足

脚本使用附带的中国大陆官网营养参考（2025-04），按明确标准份量计算；官网来源 https://www.mcdonalds.com.cn/nutrition_calculator 。不知道规格的商品、未收录新品和非标准配方设 nutritionEligible=false，不估算，不把缺失当零。脚本可能仅提供两种餐型，甚至在完全没有可核验数据时仅提供快乐餐；请向用户说明 mealStyles 的原因，不擅自放宽条件。verify 会重新计算营养，不能信任调用者传入的热量总量。不要承诺减重、增肌或营养最优。
